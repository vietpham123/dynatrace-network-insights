Installing the app — step by step

A follow-along guide for installing Network Insights into your Dynatrace tenant. No prior knowledge assumed. Seven steps, about five minutes of actual work, and nothing here touches your network devices.

~5 minutes no device impact reversible

Read the pre-deployment brief first

Four decisions to make first covers the questions to answer before installing anything — including one about IP addressing that cannot be undone afterwards. Thirty minutes, no tooling required.

Before we start — what this is

This is a custom app, not a Dynatrace Hub app. There is no button to click inside Dynatrace to install it. The source code sits in a folder on your machine, and we run one command that packages it and uploads it into your tenant.

It adds pages to your Dynatrace UI. On its own it collects nothing and talks to no network device — connecting data sources is a separate, later phase.

Two things to sort out before the session

  • The app-engine:apps:install permission on the account doing the install. Without it, step 5 fails and there is no workaround in the room — it is an IAM change on your side that cannot be made while we wait.
  • npm registry access from the machine. Step 2 downloads build tooling from the public npm registry. Corporate proxies commonly block it. This is the single most frequent reason an install session stalls.

Both are worth confirming a day ahead.

What you need on the machine

Node.js 16.13 or newer

Required

Check it:

node --version
Anything starting v16.13, v18, v20 or v22 is fine. "command not found" means Node is not installed — get it from nodejs.org first, which is its own detour.

The app source folder

Required

Provided by your Dynatrace contact as a zip or a git repository.

There is no download link inside Dynatrace for this. If you are looking for it in the Hub, you will not find it.

A browser signed in to Dynatrace

Required

The install authenticates through a browser window, not an API token you paste in.

Make sure the browser is signed in to the tenant you intend to install into. Being signed in to a different one is a common source of confusion at step 5.

A terminal

Required

Terminal on macOS or Linux, PowerShell on Windows. No administrator rights needed.

Every command below runs from the same folder. If something looks wrong, it is almost always because the terminal is in the wrong place.

The seven steps

Open a terminal in the right folder

cd network-insights-app
✓

The prompt now ends in network-insights-app.

Confirm it is the right folder:

ls
✓

app.config.json, package.json, ui and api appear in the list.

If app.config.json is missing you are one folder too high or too low. On Windows Command Prompt the command is dir, not ls; PowerShell accepts both.

Install the build tooling

npm ci
✓

A spinner, then a line like added 800 packages. One to three minutes the first time.

Say

"This downloads the toolkit that builds the app. It is a one-time thing on this machine, it writes only into this folder, and it needs no admin rights."

If it hangs or errors it is almost always a corporate proxy or an npm registry restriction — not the app. That is an IT conversation, and it is the most common place an install stalls.

Set the version number

Open app.config.json in any text editor and find the version line. Increase the last number by one, then save.

"version": "0.107.0"    →    "version": "0.107.1"
Say

"Dynatrace will not accept a version that already exists in the tenant. Every time we push an update, this number goes up. If you ever see 'version already exists', this is the fix."

While that file is open — the permissions list

Below the version is a scopes array: every permission the app holds, each with a comment explaining why it is there. That list is the complete set of things the app is able to do in your tenant. Nothing outside it is possible.

If your security team wants to review one thing before install, it is this.

Build it locally, before uploading anything

npm run build
✓

Creating bundles... with a green tick, then Done.

Say

"This packages the app without uploading it. We do it as its own step so that if anything is wrong, we find out here on your laptop rather than halfway through an upload into your tenant."

The build may also print a box suggesting package updates. Ignore it — those versions are pinned deliberately.

If the build fails, stop here. Do not run step 5. Send the terminal output to your Dynatrace contact.

Upload it to the tenant

One command. The destination is typed out in full, every time:

npx dt-app deploy --environment-url https://<TENANT>.apps.dynatrace.com/
Say

"We name the destination explicitly on every deploy. There is no default target — that is deliberate, so nobody can push to the wrong environment by accident."

✓

A browser tab opens asking you to sign in to Dynatrace and approve the toolkit. Click through it. The terminal then shows upload progress and finishes with the app name and version.

If no browser opens, the terminal prints a URL — paste it into a browser by hand.

If it fails on permissions, the account is missing app-engine:apps:install. Nothing in the terminal can fix that; it is an IAM grant on your side.

Confirm it landed, and open it

npx dt-app info
✓

Network Insights is listed, at the version you set in step 3.

Then open it — either search "Network Insights" in the Dynatrace launcher, or go straight to:

https://<TENANT>.apps.dynatrace.com/ui/apps/my.cno.networkinsights
✓

The app opens with a left-hand navigation of ten pages.

Say

"That is the install done. The pages will be sparse until we connect data sources — that is the next phase, and a separate conversation."

Say that before they see an empty page. It is the difference between "installed successfully" and "is it broken?"

Give the team access

Installing the app does not let anyone else open it. Your Dynatrace administrator grants users:

  • app-engine:apps:run — permission to open the app at all
  • the metric and log read permissions your users most likely already hold
Say

"You have installed it, and right now you are the only person who can see it. Adding your team is an IAM group change on your side, not something we do from here."

If step 5 cannot open a browser

Cloud development environments — GitHub Codespaces, Gitpod, a container over SSH — often cannot complete the browser sign-in. There are two ways to supply credentials directly. Either one short-circuits the browser flow entirely.

Try the manual paste first — it takes 30 seconds

The toolkit has explicit Codespaces support and binds its callback so port forwarding can work. When no browser opens it prints Open this url to authenticate: — paste that into any browser and finish there. If the forwarded port (5343–5363) is private, making it public is often enough on its own.

Option A — a platform token

Simplest. Set one variable and run the deploy exactly as in step 5:

export DT_APP_PLATFORM_TOKEN='<token>'
npx dt-app deploy --environment-url https://<TENANT>.apps.dynatrace.com/

The token is used as-is — no exchange, no callback, no port. It takes priority over everything else, so nothing else needs changing.

Option B — an OAuth client (recommended)

Set both variables. Setting only one leaves the toolkit in browser mode, which looks like the variables were ignored — that is the mistake people make here:

export DT_APP_OAUTH_CLIENT_ID='dt0s02.XXXX'
export DT_APP_OAUTH_CLIENT_SECRET='dt0s02.XXXX.YYYY'
npx dt-app deploy --environment-url https://<TENANT>.apps.dynatrace.com/
✓

The client needs app-engine:apps:install. If a permission is missing the error names it — the toolkit retries each one individually and reports missing permissions: <list>. Read that line rather than guessing.

Why this one is better for most organisations: an OAuth client is a first-class object in your Dynatrace IAM — scoped, reviewable, revocable, auditable. It is also the same mechanism you would use from a CI pipeline later, so nothing is throwaway.

Handling the secret

Do not put it in a .env file in the repository, and do not paste it into a terminal where it lands in shell history. In Codespaces, use repository settings → Secrets and variables → Codespaces: they are injected as environment variables when the container starts, so the deploy picks them up with nothing to export by hand.

If something goes wrong

What you seeWhat it means
version already exists Step 3 was skipped. Bump the version and run step 5 again.
Permission denied or 403 on upload The account lacks app-engine:apps:install. Your Dynatrace administrator.
npm ci hangs or fails Proxy or npm registry restriction. Your IT team, not the app.
The build fails at step 4 Stop. Do not deploy. Send the output to your Dynatrace contact.
The app opens but every page is empty Expected. Data sources are the next phase.
No browser opens, or sign-in cannot complete Common in Codespaces and containers. See "If step 5 cannot open a browser" above — paste the printed URL, or supply a token.
The browser login loops Wrong tenant URL in step 5, or the browser is signed in to a different tenant.
The old version still shows after a deploy Cached page. Hard refresh the browser.

Backing it out

The install is fully reversible and leaves nothing behind:

npm run uninstall
Say

"If you decide against it, one command removes it. It collected nothing and changed no device configuration, so there is nothing to unwind."
