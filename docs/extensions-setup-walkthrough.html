Extensions — setup and configuration

How to get data flowing: signing, uploading and activating the extensions, then creating the monitoring configurations that actually poll your devices. This is the phase that fills the app's empty pages — and unlike installing the app, this one does talk to your network equipment.

half a day, first time touches devices needs a signing CA

What an extension is, in one paragraph

An extension is a small package that tells an ActiveGate what to poll and how to turn the answers into metrics. It runs on the ActiveGate inside your network — not in the Dynatrace tenant, and not on the devices. You upload it once, activate a version, then create one or more monitoring configurations that say which devices to poll, with which credentials, and which parts of the extension to switch on.

Say

"Three separate things, and they trip people up because they sound alike: the extension is the recipe, the version activation says which recipe is live, and the monitoring configuration is the list of devices it applies to. All three have to be right."

The order matters, and each step fails silently if the one before it was skipped

Nothing here throws a helpful error. A missing CA gives you a configuration stuck at UNKNOWN; a missing feature set gives you a configuration that reports OK while collecting nothing. Do the steps in order and verify each one before building on it.

Before you start

An ActiveGate with Extensions 2.0

Required

Installed inside the network, with SNMP reachability to the management addresses of the devices you intend to poll.

Extensions run on the ActiveGate. If it cannot reach a device, no amount of configuration in the tenant will help.

An explicit ActiveGate group

Required
sudo /opt/dynatrace/gateway/agctl group set <AG-GROUP>
sudo systemctl restart dynatracegateway
A fresh ActiveGate reports its group as bare default, which does not match a configuration scoped ag_group-default. This is the single most common cause of a configuration that sits at UNKNOWN forever with no error.

A read-only SNMP credential

Required

v2c community string or v3 credentials, stored in the Dynatrace Credential Vault.

Reference it by vault ID. Never paste a community string into a ticket or a spreadsheet — it will outlive the change window.

A signing CA — one clean one

Required

One certificate authority for this project, which you will create in step 2.

A broken or expired CA in the vault can poison the whole cluster→AG certificate sync, so the ActiveGate loads zero custom CAs and every custom extension fails signature verification. Keep the vault clean; delete dead certs.

The dt-cli tool

Required
pip install dt-cli
Provides the dt command used to generate certificates and to assemble, sign and upload the extension bundle.

Two different tokens

Required

They are not interchangeable, and this catches everyone once — see the token box below.

The platform token that uploads the bundle does not carry the scope needed to activate a version. Different scope families entirely.

The two tokens, and the two domains

Which extensions to deploy

Five are available. Start with interfaces — everything else is additive, and you can add them later without redoing anything.

ExtensionWhat it gives youSource folder
custom:cno.network.interfaces Start here. Interface and device metrics — the core of the fleet view. modules/snmp-interfaces-extension/
custom:cno.network.controlplane LLDP topology discovery, BGP/OSPF adjacency. Produces the topology edges. modules/controlplane-extension/
custom:cno.network.dependency Consumes those edges and materialises them as Smartscape topology. modules/network-dependency-extension/
custom:cno.network.compliance Configuration capture and golden-config drift. modules/oxidized-extension/
custom:cno.network.netbox Inventory and power topology from NetBox, if you use it. modules/netbox-extension/

Two traps in that table. The compliance extension's folder is named after Oxidized, not after the extension — there is no modules/compliance-extension/. And controlplane and dependency are two halves of one feature: deploy only one and the topology page sits empty with nothing to blame.

The eight steps

Get the extension source

Two ways, whichever suits:

  • From the app — the Configuration page offers each extension's source as a download. Nothing else to clone.
  • From the repository — the modules/ folders listed above.
Say

"We ship the source rather than a signed binary on purpose — you sign it with your own certificate authority, so nothing runs in your environment that you did not sign yourself."

Create the signing certificates

dt ext gencerts --ca-cert ca.pem --ca-key ca.key \
                --dev-cert dev.pem --dev-key dev.key \
                --no-ca-passphrase --no-dev-passphrase

cat dev.pem dev.key > dev_fused.pem
✓

Four files, plus the fused one. Certificate first, then key — that order matters and reversing it fails later, obscurely.

Prove the chain is sound before going anywhere near distribution:

openssl verify -CAfile ca.pem dev.pem
✓

dev.pem: OK

Do this now, not later. It separates a chain-packaging problem from a trust-distribution problem, and those two look identical from the ActiveGate's error messages.

Trust the CA in the tenant

In Dynatrace: Settings → Credential vault → Certificate, scope Extensions. Upload ca.pem — the CA, not the developer cert.

Use the UI for this one. The credentials REST API rejects passwordless public certificates, so scripting this step fails for a reason that has nothing to do with your certificate.

Say

"This is the first of two places the CA has to be trusted. Only this one is obvious, and missing the second is the classic day-one failure."

Confirm the ActiveGate has picked it up

The ActiveGate syncs trusted extension CAs from the tenant into its own store. Nothing to run — but it is a genuinely separate trust stage, and it is where deployments stall.

If you seeIt means
SignatureVerifier: unable to get local issuer certificate The ActiveGate cannot build the chain — the CA has not reached its store.
Cannot extract extension … checking signature failed Trusted in the tenant, not on the ActiveGate. The second of the two places.

The reliable recovery for a stuck trust store is a clean uninstall and reinstall of the ActiveGate — a freshly installed one syncs the bundle on first boot. Blast radius is low: entities, metrics already in Grail, and OneAgent are all independent of any single ActiveGate.

Build, sign and upload

dt ext assemble --source extension --output ext.zip --force
dt ext sign --src ext.zip --output bundle.zip --key dev_fused.pem --force
dt ext upload --tenant-url "$DT_URL" --api-token "$TOK" bundle.zip
✓

The upload reports the extension name and version it accepted.

Say

"Uploading does not turn anything on. The extension is now available in your tenant and is polling absolutely nothing — that is the next two steps."

Activate the version

The active version is a single environment-wide setting. One call moves every monitoring configuration of that extension at once, however many there are.

PUT https://<TENANT>.dynatrace.com/api/v2/extensions/<name>/environmentConfiguration
{"version": "x.y.z"}

Classic dt0c01 token, environment-api:extensions:write, on the environment domain.

On an existing deployment, this is a migration — not an upgrade

Moving custom:cno.network.interfaces to 0.0.14 or above stops every pre-existing configuration collecting cno.if.*, cno.device.cpu_usage, memory and cno.power.* — while every one of them keeps reporting status OK. 0.0.14 made each OID group an opt-in feature set, and activation does not re-derive a stored empty featureSets value.

The status field is not the test. Snapshot what each configuration collects before you activate. On a first, clean deployment none of this applies.

Create the monitoring configurations

POST https://<TENANT>.dynatrace.com/api/v2/extensions/<name>/monitoringConfigurations
[{ "scope": "ag_group-<AG-GROUP>", "value": { …, "featureSets": ["Interfaces"] } }]

Three things to get right, all of them silent when wrong:

  • Scope it to the ActiveGate group — ag_group-<name>, so the poll runs only where it can reach the devices.
  • Set featureSets explicitly on every configuration. Always. See the table below.
  • Group by device class, not by site — feature sets are per-configuration, and device class is what decides them.
Say

"We group these by what the device is, not where it lives, because the feature sets differ by device type. A site with switches and a UPS in it needs two configurations, not one."

Addresses are CIDR in autodiscovery (10.0.0.5/32, not a bare IP). For per-device community strings, use one configuration group per device; a single shared community can cover a whole subnet scan.

Verify each layer before building on it

Configuration status UNKNOWN immediately after creation is normal and clears on the first poll. UNKNOWN forever with no error is almost always the ActiveGate group or the CA trust.

// devices reporting at all
timeseries n=count(cno.device.uptime), from:-10m, by:{`device.address`}
| fieldsAdd s=arraySum(n) | filter s>0 | summarize devices=count()

// interfaces reporting
timeseries n=count(cno.if.oper_status), from:-10m, by:{`device.address`,if_index}
| fieldsAdd s=arraySum(n) | filter s>0 | summarize ifaces=count()

// LLDP topology — only 'link' records are edges;
// 'device' records mean it polled fine and found no neighbours
fetch logs, from:-30m | filter `log.source`=="network.lldp"
| summarize c=count(), by:{`lldp.record`}

// topology edges, and where each one came from
timeseries e=count(cno.dep.uses), from:-30m, by:{discovery,link_type}
| fieldsAdd n=arraySum(e) | filter n>0 | fields discovery, link_type, n
✓

A non-zero device count, then a non-zero interface count. In that order — interfaces without devices means something is wrong with the query, not the poll.

Feature sets — set these explicitly, every time

Device classFeature setsNever
Switch / router / WAN edge / access point Interfaces — plus Cisco device health on Cisco—
UPSUPS power never Interfaces
PDUPDU power never Interfaces

Why a UPS must never get Interfaces

Interfaces is the only feature set that issues SNMP GetBulk. Management cards in a UPS or PDU answer GetNext in milliseconds and never answer GetBulk at all — so enabling it produces a 15-second timeout every minute, a configuration permanently in ERROR, and no power data at all.

Losing the interface table on a UPS costs you nothing: cno.device.uptime is not gated behind a feature set, so the device still appears in the fleet.

Leave UPS battery voltage switched off unless the device is confirmed to implement it. It is optional in RFC 1628, and a noSuchName response kills every other power metric in the same request.

Four things that fail silently

None of these throws an error. Every one produces a plausible-looking wrong answer, which is why they are worth reading before you deploy rather than after.

1. Feature sets are not inherited across a version change

A configuration with featureSets: [] stays [] when moved to a new version — no prompt, no warning. Every gated metric stops. The device still reports, so nothing looks broken; you simply lose half the data.

Set feature sets explicitly on every configuration, and prefer recreating configurations over migrating them.

2. The version that polls is the one on the CONFIGURATION

An extension can sit active at 0.0.14 in the environment while every device is still polled by 0.0.7, indefinitely, because the monitoring configuration pins its own version. Uploading a new bundle changes nothing on its own.

After any upgrade, check the version on each configuration — not just the environment.

3. Entities are permanent, and identity is the management address

A device entity cannot be deleted — the API returns 405 — and it never ages out; entities with 90+ days of zero data are still listed. Identity keys on the management address, so renumbering a subnet orphans every device permanently: the old addresses keep their entities forever and the new ones arrive as strangers. Two devices sharing an address collapse into one entity.

Settle addressing before onboarding at scale. If any part of the estate reuses IP space — routine after a merger, and normal for DR pairs — resolve it first. This is the only decision here that cannot be undone.

4. Secrets come back masked — and the mask round-trips safely

A GET returns secrets masked (***…***), so editing one field looks like it will write the literal mask back as the community string. Measured: it does not break polling. The platform recognises the mask and preserves the stored secret — tested with an unchanged PUT and with a field change carrying eleven masked communities on a live 11-device configuration, sustained over ten minutes.

Re-supplying secrets from your own source of truth is still the better habit — it does not depend on undocumented behaviour. But it is a preference, not a rescue. Tested on the classic /api/v2 endpoint only.

If something goes wrong

What you seeWhat it means
Configuration sits at UNKNOWN forever, no error ActiveGate group mismatch, or the CA is not in the ActiveGate trust store. Both are silent.
checking signature failed CA trusted in the tenant but not on the ActiveGate.
unable to get local issuer certificate The chain cannot be built. Run the openssl verify from step 2 first.
Status OK, but only cno.device.uptime arrives Empty featureSets. The status field is not the test.
A UPS or PDU configuration is permanently in ERROR Interfaces enabled on a management card that cannot answer GetBulk.
Topology page empty, devices reporting fine Only one half of the topology pair deployed. It needs controlplane and dependency.
LLDP polls fine, zero neighbours The devices are not advertising. On Cisco IOS, LLDP is off by default — lldp run. No monitoring product can discover an adjacency nobody advertises.
Classic API calls fail oddly Wrong domain. /api/v2 lives on the environment domain, not .apps.
Every custom extension fails signature at once A broken or expired CA in the vault has poisoned the certificate sync. Clean the vault.

Then, in the app

Once devices are reporting, open the app and assign sites and roles on the Devices page. Do it during onboarding rather than after — site scoping is the whole scale strategy, and Unassigned is the one bucket no view can help with.
